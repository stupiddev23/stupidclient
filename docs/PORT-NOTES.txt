

# ---- ClientCommandSource construction

1.21.11 added a third argument to the client command source:

    1.21.5   (ClientPlayNetworkHandler, MinecraftClient)
    1.21.11  (ClientPlayNetworkHandler, MinecraftClient, PermissionPredicate)

The mod builds one in a static initializer, so the missing argument threw
NoSuchMethodError out of <clinit> and the client came up half-initialized;
the screen-init listener then ran against unset state and died with an NPE.

tools/fixccs.py adds a static bridge on the same class that passes
PermissionPredicate.ALL (field_63208) and rewrites the call site in place at
identical length - aconst_null/getstatic/invokestatic plus four nops - so no
branch offset, stack map frame or exception range moves.  The descriptor used
for the match is the 1.21.5 one; nothing else in the jar builds this class.



# ---- @Inject bridges must return void

mixbridge declares each bridge with the descriptor Mixin expects and then
forwards to the untouched 1.21.5 handler.  For a target that grew a
parameter it also gave the bridge the target's return type and ended it with
CallbackInfoReturnable.getReturnValue() -> unbox -> return.

That is only meaningful once the injection point has run.  At @At("HEAD")
the callback still holds nothing, so TextColor.getRgb unboxed null inside the
copied handler the first time the title screen drew text:

    NPE: ... CallbackInfoReturnable.getReturnValue() is null
        at class_5251.handler$beh002$mioclient$m$$b0

Mixin discards whatever a handler returns - the value the target uses only
travels through the callback - so a handler is always void.  tools/fixbridges.py
cuts the dead tail, discards a forwarded non-void result, and rewrites the
bridge descriptor to end in )V.  The `cancellable` element is left exactly as it was.  Flipping it in place
mis-landed by one byte and produced 17 annotation attributes that ASM rejected
at mixin prepare time ("Index 283 out of bounds for length 206"), aborting the
launch before any class was transformed.  Whether it should be true is still
open; it can only be changed by rebuilding the annotation, never by poking a
byte inside it.  tools/harness/AnnCheck.java parses every class through
ClassNode, the reader Mixin uses, so that damage fails here instead.



# ---- methods that lost their return type

DrawContext.drawTextWithShadow kept its id and its parameters but stopped
returning the width it drew:

    1.21.5   (TextRenderer, String, int, int, int) int
    1.21.11  (TextRenderer, String, int, int, int) void

The title screen handler called it with the old descriptor and threw
NoSuchMethodError the moment the splash overlay drew text:

    NoSuchMethodError: 'int net.minecraft.class_332.method_25303(...)'
        at class_442.handler$bfb000$mioclient$m$$OEp0YT29...

Both call sites throw the result away (`invokevirtual ...; pop`), so
tools/fixvoidcalls.py repoints the constant pool entry at the void
descriptor and turns that pop into a nop.  Same instruction widths, so no
offset, frame or exception range moves.  A call site that used the value
would be reported instead of guessed at.



# ---- the GUI matrix stack behind DrawContext.getMatrices()

1.21.5 gave the GUI a MatrixStack and drew through it:

    class_332.method_51448()Lnet/minecraft/class_4587;

1.21.11 draws 2D through a Matrix3x2fStack, and the same accessor now
returns that instead:

    class_332.method_51448()Lorg/joml/Matrix3x2fStack;

It surfaced the moment a widget rendered:

    NoSuchMethodError: 'class_4587 class_332.method_51448()'
        at class_342.handler$bff000$mioclient$m$$To3v... (class_342.java:60778)

Repointing the calls at the new type would mean changing every helper that
takes a MatrixStack -- about 80 call sites read peek().getPositionMatrix()
-- so the 62 call sites in 18 classes are instead retargeted at
MioMatrices.get(DrawContext).  It returns a MatrixStack subclass whose
push/pop/translate/scale also apply to the context's Matrix3x2fStack, which
is what the draws that follow actually use.  One instruction for one
instruction, same stack effect, so no offset, frame or handler moves.

The compat classes are compiled from tools/compat/src against the
hand-written stubs in tools/compat/stubs by tools/build-compat.sh;
tools/fixguimatrices.py installs them and rewires the call sites.

Known gap: class_4587.method_22907(Quaternionfc) has no 2D equivalent, so
a rotation reaches the mirrored 4x4 matrix but not the 2D draw.

Still broken on the same API: the DrawContext subclass in m$$HgFhY...
calls the 1.21.5 constructor (class_310, class_4587,
class_4597$class_4598) and reads field_44658.  1.21.11 has neither; its
only public constructor is (class_310, class_11246, int, int) and the
state object sits in a package-private field.



# ---- JOML Matrix4f hides its components

The first build of the matrix-stack fix got one frame further and threw:

    IllegalAccessError: class me.mioclient.compat.MioMatrixStack tried to
    access field org.joml.Matrix4f.m00
        at MioMatrixStack.sync(MioMatrixStack.java:42)

JOML is not uniform about this.  Matrix3x2f's components are public fields,
but Matrix4f's are package-private (access flags 0x00) and only reachable
through the m00()..m33() accessors, so a 4x4 cannot be filled in from
outside org.joml.  The mirror is now built with the public 16-float
constructor and copied into the inherited matrix with
Matrix4f.set(Matrix4fc).

The stubs that let this happen are gone: tools/compat/stubs no longer
describes org.joml at all, and tools/build-compat.sh compiles the compat
layer against the same joml-1.10.8.jar the launcher puts on the classpath,
pinned by sha256.  A hand-written stub cannot drift from the real
signature or access flags that way.



# ---- SkinTextures became an asset record

Joining a world threw:

    NoSuchMethodError: 'class_2960 class_8685.comp_1626()'
        at class_742.handler$bek005$mioclient$m$$b0(class_742.java)

1.21.5 SkinTextures was a plain record of Identifiers:

    (Identifier texture, String url, Identifier cape,
     Identifier elytra, PlayerSkinType model, boolean secure)

1.21.11 rebuilt it around assets:

    (AssetInfo.TextureAsset texture, TextureAsset cape,
     TextureAsset elytra, PlayerSkinType model, boolean secure)

A TextureAsset (class_12079$class_12081) wraps the Identifier and carries
the url that used to be a component of its own, and PlayerSkinType left
the nested class_8685$class_7920 for top-level class_7920.  comp_1911 (the
url), the six-argument constructor and field_41122/41123 went with it.  It
is a redesign, not a rename.

mio used it twice: a class_742 mixin that swaps skins for the local player,
two hardcoded names and other Mio users, and a no-argument method_52814
override in the widget class.

Both are neutralised for now, which leaves vanilla skins in place:

  - the mixin handler returns immediately;
  - the method_52814 override returns super.method_52814(), so callers
    still get a real skin instead of null.

Porting the handler is not a descriptor swap.  It keeps Identifiers in
locals whose stack map frames name class_2960 and class_8685$class_7920,
three of the values it passes have to become TextureAssets, and the url
argument disappears -- so four call sites, the frames and the local types
change together.  Build the asset with the single-Identifier constructor of
class_12079$class_12082 (iu$b) and the record with its five-argument
constructor.

tools/fixskins.py performs both edits and reports any other method that
still reaches the removed API instead of guessing at it.



# ---- the custom renderer targets the 1.21.5 blaze3d pipeline

The first in-game frame threw:

    NoSuchMethodError: 'void RenderSystem.setShaderColor(float, float,
    float, float)'
        at me.mioclient.m$$3uGlx...m$$U07Rr2ofjRcmUA6QhPzXslX...
        at class_329.handler$bdf000$mioclient$m$$sLWT6...

com.mojang.* is not remapped to intermediary, so a Mojang-side change
surfaces as a plain NoSuchMethodError with nothing to bridge.  Auditing
every com.mojang member the jar calls against client.jar finds twelve
methods and thirty calls, all one subsystem -- mio's custom HUD renderer:

    RenderSystem.setShaderColor(FFFF)V          gone, colour is a uniform now
    RenderSystem.getShaderColor()[F             gone
    RenderSystem.setShaderTexture(int,GpuTexture)V   moved to RenderPass
    RenderSystem.enableScissor(IIII)V           -> enableScissorForRenderTypeDraws
    RenderSystem.disableScissor()V              -> disableScissorForRenderTypeDraws
    RenderSystem.lineWidth(F)V                  gone
    RenderSystem.getProjectionMatrix()          gone, it is a GpuBufferSlice now
    RenderSystem.shaderLightDirections          gone, it is a GpuBufferSlice now
    RenderPipeline.Builder.withUniform(String, class_10789)      changed
    RenderPipeline.Builder.withVertexFormat(VertexFormat,...)    changed

1.21.11 moved colour, texture binding, scissor and line width onto
RenderPass and per-pipeline uniforms, and changed the builder, so this is
a rewrite against the new GPU abstraction rather than a rename.  The
renderer is one facade class with 23 overloads reached from 86 call
sites, so stubbing it piecemeal would blank mio's whole custom HUD and
still leave two non-void accessors returning float[] and Vector3f
unresolved.  It is left alone until it can be ported properly.

tools/fixmojang.py re-runs the audit against client.jar, prints what is
missing, and can stub void methods that call removed members (it refuses
constructors, class initialisers and anything that has to return a
value).  Use --list before deciding.
